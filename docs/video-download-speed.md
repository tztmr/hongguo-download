# 视频下载速度与备用线路

视频下载复用已有 CDN 连接池。此前备用地址只检查首包等待：一旦收到首包，后续卡住或持续低速时只能等该请求完成／超时，拖住下载队列。

整个传输期间监测进度：首包等待 2 秒或已有数据后停顿 3 秒时，尝试备用地址。每集最多同时使用两条线路；只有完整、通过现有校验的响应才成为结果，其余请求及时关闭。持续收到数据时不拉取备用副本，保留原有并发设置、清晰度和解密流程。

## 下载连接池超时恢复

`PoolTimeout` 表示等待本地连接池名额超时。旧逻辑把它记成某个 CDN 下载失败，并把本地排队时间计入首包等待，可能为同一集额外启动备用请求，加重排队。

现在通过 HTTPX 的传输事件区分本地排队和实际连接过程：取得连接并开始网络操作后才计时首包等待。连接池超时后保留原地址，间隔 0.5 秒、1 秒重试，最多重试两次，整个下载仍受 120 秒总超时约束。仍无法取得连接时返回 HTTP 503、业务码 `-11` 和 `Retry-After: 5`，显示“下载连接繁忙，请稍后重试”。此类繁忙不会刷新播放地址或继续枚举 CDN，下载队列可按已有策略重新调度；其他 CDN 错误保留原有切换逻辑。

下载名额排队、播放地址解析、CDN 传输和失败重试等待均检查客户端是否断开，适用于普通下载及在线播放。请求断开后取消对应网络任务、关闭流并释放名额；不影响其他下载。界面中的“暂停队列”仍按原有语义停止派发新任务，已经派发且连接仍保持的下载可以继续收尾。

回归测试使用真实本地 HTTP 连接复现连接池耗尽，验证释放连接后的原地址重试、持续繁忙的有界失败、排队取消、传输取消以及取消后的下一集下载。Windows 和 macOS CI 均包含这些测试。关于超时及传输事件的定义见 [HTTPX 超时文档](https://www.python-httpx.org/advanced/timeouts/) 和 [传输事件文档](https://www.python-httpx.org/advanced/extensions/#trace)。此修复需要重新打包内置 API 才会进入安装版。

## v0.3.1 相比 v0.2.6 的速度回退修复

v0.3.1 曾增加“传输超过 8 秒、平均速度不足 256 KiB/s 就尝试备用源”的规则。多集共享带宽时，单集低速不代表 CDN 异常；这条规则会为仍然正常传输的剧集下载第二份内容，挤占有效带宽。Windows 和 macOS 使用同一个 `core/video_download.py`，都会受影响。

现已移除固定速度阈值，恢复 v0.2.6 对持续传输的处理方式，同时保留首包超时、中途停顿和请求失败时的切换。持续低速但不断收到数据的线路不会再抢跑备用源，仍受整集 120 秒超时限制。

2026-09-12 使用真实本地 HTTP 连接、合成内容进行对比：8 集各 1 MiB，共享限速 512 KiB/s。v0.2.6 约 18.10 秒、8 次请求、8 MiB；修复前 v0.3.1 约 27.94 秒、16 次请求、12.40 MiB；修复后约 18.01 秒、8 次请求、8 MiB。三组均校验完整内容一致。这说明共享带宽场景中的重复流量已消除，不代表真实用户网络或 CDN 能达到固定速度。

验证包含首包停顿、中途停顿、持续低速不重复下载、正常持续传输、备用数据无效、两条线路上限以及取消时释放连接。`scripts/verify-download-failover.py` 使用真实本地 HTTP 连接和合成内容，模拟主线路首包后暂停 6 秒：v0.2.6 约 6 秒完成，修复后约 3 秒取得完整备用内容。

可重现：

```sh
python3 -m unittest tests.test_video_download -v
python3 scripts/verify-download-failover.py
python3 scripts/verify-download-bandwidth.py
# 可用 --baseline /path/to/old_video_download.py 对比旧实现。
# bandwidth 支持重复传入 --baseline，分别对比 v0.2.6 和修复前 v0.3.1。
```

此修复位于内置 API。macOS 和 Windows 安装包都需重新打包 API 辅助程序，并通过源码指纹检查；仅替换网页资源不会生效。
