# 媒体任务并发调度（v0.2.5）

## Windows CPU / GPU 混合调度（2026-09-13 源码更新）

AI 设备设为“自动”时，优先让 GPU 推理；显存不足或 GPU 利用率达到 85% 时，调度器检查 CPU 和模型所需内存，将新的任务交给 CPU。已经启动的任务保持原设备，不在运行中迁移模型；原有“自动”偏好也不会被改写。手动指定 CUDA 的任务不会被调度器改为 CPU。CPU 接手的任务在进度中显示 `CPU ·`。

分离和字幕可分别使用 CPU / GPU 同时处理。单个任务也会用 CPU 做音频预处理和结果写入、用 GPU 执行模型推理；这不等于把 CPU 和 GPU 的算力相加用于同一次模型计算。GPU 忙时的 CPU 接手仍检查完整模型内存估算、CPU 空闲量和线程预算，自动最多 5 个任务，手动最多 10 个。

手动指定并发数但设备仍设为“自动”时，同一轮新启动任务按完整模型估算预留内存和显存，避免模型尚未加载时连续启动多个 GPU 任务、重复占用同一份空闲显存。

手动并发不再固定每个任务 1 个线程：按逻辑核心数的 85% 除以设置的并发数分配，每个任务 1–8 个线程。例如本次测试的 i5-14600KF（20 逻辑线程），并发 1 个分配 8 线程、并发 5 个分配 3 线程。Windows Job Object 继续根据实际活动任务数动态限制总 CPU 占用。线程池大小在任务启动时确定；减少活动任务会放宽 CPU 配额，但不会扩张已启动的线程池。

CUDA 架构筛选识别同一计算能力主版本的向前二进制兼容，以及 `compute_XX` / `+PTX`，通过筛选后仍执行真实张量运算。依据：[NVIDIA CUDA 平台兼容规则](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html)。

分离在 CUDA OOM 后只重试当前未写入的段：先缩短 Demucs 内部推理长度，后续段沿用成功的长度；再次失败则恢复原长度并改用 CPU。正常任务的推理长度不变，短上下文只用于显存不足时的恢复，音质仍需在业务素材上评估。字幕直接读取已经准备好的 16 kHz 单声道 PCM，减少一次 FFmpeg 启动和重复解码；自动设备在 GPU 推理失败后允许一次 CPU 重识别，不发布失败任务的半成品字幕。

本次实测：Windows、i5-14600KF、RTX 5060 Ti 8GB、驱动 610.74、Torch 2.7.1+cu128、Demucs 4.0.1、Whisper 20250625。约 11 秒公共语音样本在 CUDA 上完成字幕识别及分离；GPU 字幕与 CPU 分离并发也成功。完整 AI 测试通过 42 项，包含真实模型及模拟一次 OOM 后的真实 CUDA 短片段推理。这些是短样本功能验证，不代表长剧吞吐量或加速倍数。

此次修改为源码：桌面调度更新需重新构建桌面程序，Python 更新需重新打包 AI worker。现有安装的 v4 worker 不会自动采用新 Python 代码；发布时应生成新版本组件归档和真实校验值，再更新组件清单。

以下为此前版本记录；与上面的线程及回退行为有冲突时以上述更新为准。

Windows 的媒体处理页、批量分离／提取字幕弹窗和设置页提供“AI 同时处理”：自动（最多 5 个）或手动 1–10 个。分离与字幕共用名额，设置写入本地配置，下次启动恢复。每个任务对应一部剧；选择逐集处理时，同一任务里的各集仍按顺序处理。

队列采用滚动补位：任意任务完成、失败、取消或删除后，空位可启动下一个排队任务，不等待同批全部结束。降低上限不取消正在运行的任务；暂停的任务保留名额和模型内存。合并视频保持独占、按顺序执行，队列不会跳过前面的合并任务。

## Windows 资源控制

- 自动模式保留模型内存预估、CPU / GPU 利用率检查。读取的是实时可用内存和显存，不再重复减去运行中任务的整份预留量；同一轮新启动任务仍扣除预留量，避免一轮重复使用相同空闲资源。
- 手动模式按指定名额启动，替代保守的模型预估限制；可用内存低于 2 GiB 或可用显存低于 1 GiB 时暂停补位。读不到显卡指标时，手动模式仍允许并发。名额是上限，不保证所有设备都能安全或高效地跑满。
- 媒体处理页显示等待并发名额、内存／显存、自动资源检查或独占合并任务等原因。约每 2 秒重查资源，任务结束和设置更改会主动唤醒调度器。
- Windows 工作进程的 Torch / BLAS 线程池可使用最多 16 个逻辑线程，通过 Job Object 动态分配 CPU 上限，总预算为机器 CPU 的 85%。5 个活动 AI 任务时每个最多 17%，只剩一个时可使用 85%；硬件核心数和任务本身仍会限制实际占用。
- 配额在运行中调整，不重启当前任务。GPU 失败回退到 CPU 的任务能使用随后释放的 CPU 容量，无需重新下载 Windows v3 AI 运行环境。此次没有修改既有工作程序在同一输入内保留 CPU 回退的行为。
- Windows 合并需要 CPU 转码时，x264 从 medium 改为 fast，保留原有 CRF 档位（18／23／28）。压缩效率可能变化，输出体积可能增大。无损拼接及 NVENC 路径保持原样；需要重新编码的任务仍会比无损拼接慢。

macOS 的并发策略和线程限制保留原状：音频分离自动调度、最多 5 个；字幕和合并独占。共享的运行环境和模型在最后一个任务结束前保持“使用中”。

实现依据：[Microsoft Job Object CPU 配额](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information)、[sysinfo CPU 采样间隔](https://docs.rs/sysinfo/latest/sysinfo/constant.MINIMUM_CPU_UPDATE_INTERVAL.html)。
