# 红果下载：媒体任务暂停、删除与重复合并保护设计

日期：2026-09-06

## 目标

为下载管理页中的媒体处理任务补齐可控的生命周期，并阻止同一剧目在已有合并成品时再次发起合并：

1. 排队中的媒体任务可以暂停和继续。
2. 运行中的 FFmpeg、Demucs 和 Whisper 任务可以原地暂停，同一应用会话中继续时从当前处理位置恢复。
3. 任意媒体任务都可以删除任务记录；删除运行中任务时先可靠停止底层进程。
4. 剧目目录中已有合并视频时，界面禁用“合并视频”，原生后端也拒绝重复请求。

本设计适用于合并视频、分离背景音乐和提取字幕。普通视频下载任务的暂停、删除规则不在本次改动范围内。

## 与现有规格的关系

本设计增量修改 `2026-09-02-media-processing-youtube-upload-design.md` 中的媒体任务状态和合并冲突规则。

- 新增 `paused` 状态以及暂停、继续、删除操作。
- “输出已存在时允许覆盖或另存”的旧规则，由本设计的“只要剧目存在合并成品就禁止再次合并”取代。
- 删除媒体任务仍只删除任务记录和该任务尚未发布的临时文件，不删除下载源文件、已经完成的合并视频、音频分离成品或字幕。

## 用户交互

媒体处理列表按任务状态显示操作：

| 状态 | 可用操作 | 行为 |
| --- | --- | --- |
| `queued` | 暂停、删除 | 暂停后不再被工作线程领取；删除立即移除记录 |
| `running` | 暂停、删除 | 暂停底层进程；删除先终止进程，再移除记录 |
| `paused` | 继续、删除 | 继续排队或恢复被挂起的进程；删除按暂停来源处理 |
| `completed` | 删除 | 只移除记录，保留成品 |
| `failed`、`cancelled`、`interrupted` | 重试、删除 | 重试沿用现有语义；删除立即移除记录 |

“暂停”成功后按钮变为“继续”，任务阶段和百分比保留。“继续”不创建新任务记录。

已完成下载的剧目按真实文件状态显示合并入口：

- `合并视频/` 中没有合并成品时，按钮可用。
- 目录中存在任意普通 `.mp4` 文件时，按钮禁用并显示“已合并”。扩展名判断不区分大小写。
- 用户在 Finder 中删除所有合并成品后，下一次刷新状态时按钮重新可用。

## 状态模型

`MediaJobStatus` 新增 `Paused`。任务同时持久化可选的暂停来源 `pause_origin`：

- `queued`：任务在等待队列中被暂停。
- `running`：任务执行进程已被挂起。

合法转换如下：

```text
queued  --pause--> paused(origin=queued) --resume--> queued
running --pause--> paused(origin=running) --resume--> running

queued/running/paused/terminal --delete--> removed
```

现有的完成、失败、取消、重试转换保持不变。管理器必须拒绝不合法转换并返回稳定错误码，不能只由界面隐藏按钮来保证状态正确。

进度更新允许任务处于 `running` 或 `paused(origin=running)`。这样可以吸收暂停信号与最后一次进度事件之间的竞争，不会把正常暂停误判为任务失败。

## 进程暂停与继续

媒体执行层增加一个任务级 `ProcessControl`，统一负责取消、暂停状态和当前子进程注册。FFmpeg、ffprobe、AI worker 以及它们的子进程在独立进程组中启动，并在启动后立即注册进程组 ID。

运行中任务暂停时：

1. 服务先把控制器标记为暂停，防止新的阶段进程继续运行。
2. 对当前进程组发送 `SIGSTOP`。
3. 信号发送成功后把任务持久化为 `paused(origin=running)` 并通知界面。

继续时：

1. 对已注册进程组发送 `SIGCONT`。
2. 清除控制器暂停标记。
3. 把任务持久化为 `running` 并通知界面。

如果任务在两个子进程阶段之间收到暂停请求，执行器在启动下一进程后立即检测暂停标记并将新进程组挂起。这样暂停不会因阶段切换而失效。

本应用当前交付目标是 macOS，因此使用 POSIX 进程组信号。信号发送失败时不改变持久化状态，并返回可重试错误。暂停不会通过结束进程和重新排队来模拟。

## 重启恢复

应用退出后无法保证操作系统仍保留被挂起的子进程，因此恢复规则区分暂停来源：

- `paused(origin=queued)` 在重启后仍保持暂停，用户点击继续后回到队列。
- `running` 和 `paused(origin=running)` 在载入快照时转为 `interrupted`，用户可从头重试。

同一应用会话内的暂停和继续为原地恢复；跨应用重启不承诺从媒体编码或 AI 推理的中间位置续跑。

## 删除任务

删除只影响任务记录：

- 排队、排队暂停和终态任务由 `MediaJobManager` 立即从快照中移除并原子持久化。
- 运行中或运行暂停任务先进入“待删除”集合。服务发送继续信号解除挂起，再触发取消并终止整个进程组。工作线程确认退出后清理任务私有临时目录、移除记录并持久化。
- 待删除任务停止发送进度和终态事件，避免前端已经移除的记录再次出现。
- 删除接口返回后，前端立即移除对应行；后端完成延迟清理后，后续快照中也不再包含该任务。

删除不得移除输入视频、剧目目录中的元数据与封面、正式发布的合并视频、音频分离输出或字幕。只有任务自己的未完成临时目录可随取消清理。

## 重复合并保护

重复合并使用文件系统作为权威状态，不能依赖媒体任务记录，因为用户可以删除任务记录但保留成品。

新增只读原生命令查询某个剧目是否已有合并成品。检查规则为：

1. 规范化并验证剧目根目录。
2. 只检查该根目录下真实的 `合并视频/` 目录，不跟随符号链接到目录外。
3. 任意非符号链接的普通 `.mp4` 文件都视为已合并。

界面在下载批次完成、媒体任务完成或删除、以及页面重新载入时刷新该状态。查询结果为真时禁用“合并视频”。

`start_merge` 在创建任务前执行同一检查；发现成品时返回稳定错误码 `MERGE_OUTPUT_EXISTS`。这个后端检查用于处理界面状态过期或并发点击。新合并请求固定使用 `FailIfExists`，界面不再提供覆盖选项。为读取旧任务快照可以暂时保留 `Overwrite` 枚举的反序列化兼容，但新请求不得选择它。

用户手动移走或删除 `合并视频/` 下所有 `.mp4` 后，可以再次合并。删除媒体任务记录本身不会解除保护。

## 原生命令与前端接口

新增命令：

- `pause_media_job(job_id)`
- `resume_media_job(job_id)`
- `delete_media_job(job_id)`
- `has_merged_video(series_root) -> bool`

`useMediaJobs` 暴露对应操作，并在命令失败时恢复乐观更新前的状态。`MediaJobsPanel` 根据任务状态显示暂停、继续、删除或重试按钮，并为运行中的删除显示短暂的“正在停止”。

合并按钮的禁用状态由 `has_merged_video` 返回值驱动；`start_merge` 的 `MERGE_OUTPUT_EXISTS` 错误仍需转成明确中文提示，不能显示原始系统错误。

## 并发与一致性

- `MediaJobService` 继续一次只执行一个重型媒体任务。
- 暂停运行中任务不会让后续任务越过它启动；工作槽仍由被挂起任务占用。
- 暂停排队任务会被领取逻辑跳过。
- 删除当前运行任务后，只有在其进程确认退出并释放工作槽时，下一项排队任务才开始。
- 暂停、继续、删除和工作线程完成事件都通过管理器的单一状态锁串行修改快照。
- 合并输出检查和任务入队必须在服务级临界区内连续执行，避免两次快速请求同时通过检查。

## 错误处理

对界面提供稳定、可识别的错误码：

- `MEDIA_JOB_NOT_FOUND`
- `MEDIA_JOB_INVALID_TRANSITION`
- `MEDIA_JOB_SIGNAL_FAILED`
- `MERGE_OUTPUT_EXISTS`

错误摘要只包含任务 ID、阶段和安全路径摘要，不记录完整命令行、OAuth 数据或模型下载凭证。暂停或继续失败时保留原状态；删除进程失败时保留任务记录并显示失败原因，不能在进程仍运行时伪报已删除。

## 验证

Rust 单元与集成测试覆盖：

1. 所有合法和非法状态转换，以及暂停来源的序列化与重启恢复。
2. 排队暂停任务不会被领取，继续后恢复排队。
3. 使用写入心跳文件的测试子进程验证 `SIGSTOP` 后心跳停止、`SIGCONT` 后从同一进程继续。
4. 暂停发生在两个处理阶段之间时，新子进程仍立即挂起。
5. 删除运行或运行暂停任务会终止进程组、清理临时目录并移除记录，且不会删除正式输入或输出。
6. 删除与完成同时发生时不会让任务记录重新出现。
7. `合并视频/` 中存在普通 `.mp4` 时查询和 `start_merge` 都拒绝；符号链接、其他扩展名和目录外文件不误判。
8. 删除所有合并 `.mp4` 后允许新合并请求。

前端测试覆盖按钮随状态变化、暂停/继续/删除命令调用、失败回滚、已有合并成品时禁用入口，以及后端竞争错误的中文提示。

最终验证使用一组短视频执行合并、暂停、继续和删除，并对 FFmpeg 与 AI worker 各验证一次真实进程暂停。打包前运行现有 Rust、前端和 Python 回归测试，确认下载、媒体处理、AI 模型管理和已有音画同步修复未被破坏。

## 完成标准

- 用户可以暂停、继续和删除所有媒体处理任务，界面与持久化状态一致。
- 运行中任务暂停后 CPU/GPU 处理实际停止，继续后由同一子进程向前运行。
- 删除运行中任务不会遗留活跃子进程，也不会删除用户成品。
- 只要剧目 `合并视频/` 中仍有 `.mp4` 成品，界面和原生后端都不能再次发起合并。
- 应用重启后的恢复行为符合暂停来源规则，且旧任务快照仍可读取。
