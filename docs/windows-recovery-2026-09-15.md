# Windows 页面与下载恢复修复记录

基于用户最新推送 `d3eb18086716763501d7eaec39377108efc8dedc`（v0.4.9）。保留整部剧完成正片、Shorts、清理后才释放组名额的规则。

## 修改与证据

| 问题 | 已定位的问题与修改 |
| --- | --- |
| WebView2 页面卡顿 | 自动追剧状态读取、控制、审核以及媒体任务读取、提交合并的同步命令可能在窗口线程上等待持锁的磁盘写入，改到后台线程。轮询仅返回页面使用的任务字段，不再携带各集路径、哈希、完整 AI 结果。手动下载队列忽略自动下载进度及无变化事件。 |
| 媒体检测无效 | 统一两平台的解析：支持数字/字符串时长、`duration_ts × time_base` 的有效时长，以及 `r_frame_rate` 不可用时的有效平均帧率；保留真实视频流、编码、宽高和时长检查。Windows 错误显示具体原因、文件名和字节数。 |
| Windows 路径 | 合并清单原先把规范化路径中的 `\\?\` 替换为 `//?/` 后交给 URL 相对路径解析。现在明确使用 `file:`，保留反斜杠及长路径前缀，单独转义单引号，拒绝换行等控制字符。 |
| 无凭据同名文件 | 下载阶段的旧“无完成凭据”待核对状态自动迁移到恢复队列。已有文件先检查 MP4 数据长度，再检测媒体、计算哈希、补写凭据；完整文件复用，不完整文件移到 `.mp4.incomplete-*` 保留后重下。检测工具错误保留原文件。 |
| 确认继续后等待 | 清除旧重试时间和计数；明确提示运行中还是等待全局恢复。不因下载文件核对而跳过上传查重。恢复和进入合并前检查已记账的单集，从第一个缺失或不完整单集继续，保留后面的文件供复用。 |
| 下载大小与中断 | HTTP 字节数核对、MP4 顶层 box 长度核对、落盘同步通过后才原子替换目标文件。使用 64 位长度和 seek 跳过媒体数据，校验不把整个大视频读入内存；接纳单集时复用已经计算的哈希。 |

路径处理参照 [FFmpeg concat 文件解析](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/concatdec.c) 和 [Windows 文件名处理](https://github.com/FFmpeg/FFmpeg/blob/master/libavutil/wchar_filename.h)。媒体流选择与输出字段参照 [ffprobe 官方文档](https://ffmpeg.org/ffprobe.html)。

## 本地验证

- `npm test -- --run`：47 个文件、382 项通过；`npm run build` 通过。
- 带真实 FFmpeg/ffprobe 的 Rust 全量测试：401 项通过，6 项原有忽略测试。
- `cargo clippy --all-targets -- -D warnings` 通过；`git diff --check` 通过。
- 真实合并：超过 260 个 UTF-16 单元的中文路径、空格及单引号文件名，智能合并输出时长和逐帧哈希一致。已有时间基归一化与 Shorts 合并回归也通过。
- 大小验证：超过 4 GiB 的稀疏 MP4 外层结构样本验证 64 位长度与跳过数据的逻辑；这是容器长度测试，不是完整视频解码测试。
- 进度压力测试：1000 条自动下载事件未触发手动队列额外渲染或 localStorage 写入。
- 状态载荷测试：单任务含 300 个文件凭据及 1 MB AI 结果时，页面载荷低于 4 KB，磁盘恢复记录仍完整。
- 浏览器：1920×1080 预览下切换自动追剧设置页正常，截图位于 `output/playwright/windows-fixes-automation.png`。

测试运行在 macOS arm64；Windows 合并实现通过同文件测试模块在本机执行。未在用户的 Windows 11 / i5-12400F / GTX 1660 SUPER 电脑上运行，也没有用户报错单集样本，因此不能据此声称已复现全部现场故障或确认 WebView2 实机流畅度。按用户要求仅推送代码，提交使用 `[skip ci]`，不启动 Windows CI 或生成安装包。
