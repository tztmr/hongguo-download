# Windows 智能合并与性能（v0.2.6）

## 2026-09-13 加速更新

需要 NVENC 转码时，输入先尝试 CUDA/NVDEC 解码，CPU 继续处理帧率、缩放、填边和音频，NVENC 完成编码。GPU 解码故障会重做当前中间片段，并在后续片段使用 CPU 解码，保留 NVENC 编码；NVENC 本身故障仍按原流程统一回退 CPU 编码。磁盘及权限错误不会触发解码重试。同一片段重试时进度不倒退。

参数兼容的视频仍走无损复制，避免无必要转码。本次在 RTX 5060 Ti 8GB 上验证了 CUDA 解码与 NVENC 编码，并运行不同画面尺寸、时间基准、音频参数及无音轨的实际 FFmpeg 合并测试。Windows 媒体核心测试共 23 项通过；使用独立测试入口直接编译项目的媒体源码，不等同于整个 Tauri 安装包构建通过。未给出长视频性能倍数。

v0.2.3 与 v0.2.5 的 NVENC 参数相同。v0.2.5 只将 CPU x264 preset 从 medium 调为 fast，因此不能把某一批视频的变慢简单归因于升级。

旧 Windows 实现在各集参数不同后，仍直接把原文件交给 concat demuxer，再对整条输入流转码。concat 要求流参数（包括时间基准）一致。可复现样本：两段各 1 秒、同样 12 fps 的 H.264，时间基准分别为 1/12288 与 1/90000，旧路径输出约 13.583 秒，触发总时长验证失败。[FFmpeg concat 文档](https://ffmpeg.org/ffmpeg-formats.html#concat)

v0.2.6 的 Windows 路径：

- 参数一致时仍走单次无损拼接。
- 视频编码配置相同，只有时间基准或音频参数不同时，保留视频数据，统一时间基准至 90000，并按每集画面时长整理音频。PCM 中间音频只在最终拼接时编码一次 AAC，避免每集编码延迟累计。
- 分辨率、帧率等不兼容时，各集独立统一至第一集的画面规格，再拼接。NVENC 失败会用 CPU 从头重做，避免混用编码配置。
- 媒体参数检测最多并行 4 个进程；进度持续显示无损、音频整理、GPU 或 CPU 编码阶段。
- 输出验证仍检查时长，不以放宽阈值掩盖问题；失败显示预期时长、实际时长、差值和集数。

输入、临时合并文件（剧目目录内 `.hongguo-merge-*`）和最终输出（剧目目录内 `合并视频`）都跟随剧目目录。安装目录或 C/D 盘符本身不会改变合并算法。临时目录增加进程内唯一序号，避免同时创建时同一系统时钟刻度发生名称冲突。

测试使用真实 FFmpeg，覆盖不同时间基准、音频采样率、声道、无音轨、分辨率和帧率。无损路径逐帧校验，转码路径检查输出尺寸、帧数和时长。Windows 发布流程使用打包的 FFmpeg 运行这些测试；本机 macOS 仅在测试时编译 Windows 合并逻辑，macOS 的生产合并路径未修改。
