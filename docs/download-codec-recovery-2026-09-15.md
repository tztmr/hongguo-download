# 自动追剧 ByteVC2 下载恢复

用户报告第 3 集 `0003_7678806141064711230_720p.mp4`（5,972,218 字节）报“媒体检测失败：无法识别音视频编码”。重新请求同一集并下载后复现：MP4 结构、文件长度和时长均有效，视频编码标记为 `bvc2`，打包的 FFprobe 没有返回 `codec_name`。源模型明确给出 `bytevc2`，与解密后的 `bvc2` 编码标记一致。

该集 360p、480p、540p、720p 都是 ByteVC2，1080p 是 ByteVC1 / HEVC。旧选源逻辑只考虑清晰度，选中 720p ByteVC2；自动追剧恢复又反复检测这个已存在的文件，无法更换下载源。

## 修复

- `/api/duanju/download` 在清晰度匹配前筛选可处理的编码；仍优先目标清晰度，然后按已有规则先降档、再升档。同档兼容源存在时不会无故升档。没有兼容源时返回明确错误，不下载明知无法解码的视频。`content`、`key` 接口保留原始源能力。
- 检测到 `bvc2` 且工具无法识别时返回 `MEDIA_CODEC_UNSUPPORTED`，区分编码不支持、工具缺失、无效 JSON 和其他媒体损坏。
- 自动追剧将原文件保留为 `.mp4.unsupported-N`，仅重下当前集；兼容文件完成格式、媒体信息和内容身份校验后才写完成凭据。已有备份不会被覆盖，未知工具错误不会触发文件改名。

## 实测

| 项目 | 修复前选源 | 修复后选源 |
| --- | --- | --- |
| 请求清晰度 | 720p | 720p |
| 实际清晰度 | 720p | 1080p |
| 文件大小 | 5,972,218 字节 | 17,788,218 字节 |
| 视频 | bvc2，无法识别 | HEVC / hvc1，1882×1080 |
| 音频 | AAC | AAC |
| 视频时长 | 109.6 秒 | 109.6 秒 |

修复后使用真实上游数据，经 API 下载路由取得兼容视频，响应头返回实际 `1080p` 和匹配的 Content-Length；本地打包 FFprobe 可识别，FFmpeg 对完整音视频解码退出码为 0，无错误输出。此集没有兼容的低档位，因此文件变大是源选择结果。脱敏证据与 SHA-256 见 [验证数据](examples/2026-09-15-bytevc2-recovery.json)，不包含密钥、设备凭证或签名 CDN 地址。

55 项 Python 测试（启用真实 FFmpeg 播放回归）、404 项 Rust 测试通过，6 项可选集成测试未运行，Clippy 全目标检查通过。Rust 全量测试在基于 `cc6f053`、只应用本次修复的独立副本中执行，排除工作区并行修改的调度测试。

本次仅提交源码，不重建 API 二进制、不打 Windows 安装包、不运行 CI。Windows 生效需要后续同时打包 Python 下载端和 Rust 恢复逻辑；本地实测不代表 Windows 安装版已验证。
